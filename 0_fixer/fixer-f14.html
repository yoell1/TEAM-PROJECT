01기능 정의와 정책

한 문장 정의

USER_ROLE = 'FIXER' 로 가입한 사람이 자기소개 · 경력 · 활동지역 · 수리분야 · 자격증을 제출하면, FIXER_PROFILE.FIXER_APPROVAL = 'PENDING' 상태로 등록되어 관리자 승인을 기다린다.

건드리는 테이블 4개

버튼 한 번에 1 + N + N + N 건이 저장된다. 이것이 이 기능의 핵심 난이도.

테이블역할건수
FIXER_PROFILE기사 본체 (소개·경력·승인상태)1건 (USER_ID가 PK → 1:1)
FIXER_LICENSE자격증 (파일 업로드 포함)N건
FIXER_REGION활동 지역N건
FIXER_CATEGORY수리 가능 분야N건

확정 정책 — 상태 기반 분기

단순히 "행이 있냐 없냐"가 아니라 "어떤 상태냐"로 판단한다. 그래서 매퍼는 count가 아니라 DTO를 통째로 가져온다.

현재 상태동작DB 작업
프로필 없음신청 가능INSERT
PENDING차단 — "이미 심사 중인 신청이 있습니다"없음
APPROVED차단 — "이미 인증된 기사입니다"없음
REJECTED재신청 가능UPDATE + 자식 DELETE → 재INSERT
중복신청 ≠ 재신청

중복신청은 PENDING/APPROVED 상태에서 또 신청하는 것 — 무조건 막는다.
재신청은 REJECTED 상태에서 다시 신청하는 것 — 정책상 허용하기로 결정.

화면 · 서버 이중 검증

위치역할
Controller (GET)이미 신청했으면 폼을 안 보여줌 — 사용자 편의(UI)
Service저장 직전 재확인 후 예외 — 무결성 방어
DB 제약PK_FIXER_PROFILE, CHECK — 최후의 방어선

화면을 우회해 POST를 직접 쏘는 경우가 있으므로 화면 검증 ≠ 서버 검증. 둘 다 필요하다.

02데이터베이스

계정 C##RR / 비밀번호 RR · Oracle SQL Developer 사용.

원본 ERD 스크립트를 그대로 쓸 수 없었던 이유
  • 백틱(`) — MySQL 문법. Oracle에 없음
  • 인라인 COMMENT '...' — Oracle은 COMMENT ON COLUMN 을 따로 씀
  • DATETIME — Oracle에 없는 타입 → TIMESTAMP
  • FIXER_PROFILE 만 INT/VARCHAR (MySQL 타입) 사용
  • FIXER_PROFILE 에 PK 제약 누락
  • USERS, CATEGORY, ADMIN 에 닫는 괄호 중복 (문법 오류)
  • USER_ADDRESS.IS_DEFAULT 에 DEFAULT NUMBER(1) (깨진 구문 → DEFAULT 0)

실행 순서

① CREATE TABLE 전부 → ② PK 전부 → ③ FK 전부 → ④ 시퀀스 → ⑤ 기초 데이터

FK는 부모의 PK가 존재해야 걸 수 있으므로 순서가 중요하다. 삭제는 정확히 반대 순서(자식 → 부모).

SecurityConfig — 시큐리티 기본 기능 끄기

com.fixer.common.config.SecurityConfig

@Configuration
@EnableWebSecurity
public class SecurityConfig {

	@Bean
	public SecurityFilterChain filterChain(HttpSecurity http) {

		http.csrf(AbstractHttpConfigurer::disable)
			.formLogin(AbstractHttpConfigurer::disable)
			.httpBasic(AbstractHttpConfigurer::disable)
			.logout(AbstractHttpConfigurer::disable)
			.authorizeHttpRequests(auth -> auth.anyRequest().permitAll());

		return http.build();
	}

	@Bean
	public PasswordEncoder passwordEncoder() {
		return new BCryptPasswordEncoder();
	}
}
줄역할
csrf(disable)위조 방지 검사 끄기 — 켜져 있으면 JS 요청이 막힘
formLogin(disable)기본 로그인 화면 끄기
httpBasic(disable)브라우저 팝업 로그인 끄기
logout(disable)기본 로그아웃 끄기
anyRequest().permitAll()모든 주소 통과 허용
passwordEncoder()Security를 넣은 진짜 이유 — BCrypt 비밀번호 암호화

BCrypt — ① 되돌릴 수 없다(단방향) ② 같은 비밀번호도 매번 다른 값이 나온다(salt). 검증은 passwordEncoder.matches(평문, 암호문) 로 한다.

FileUploadUtil — 파일 저장 · 삭제

com.fixer.common.util.FileUploadUtil

@Component
public class FileUploadUtil {

	public SavedFile save(MultipartFile file, String uploadDir, String webPrefix)
			throws IllegalStateException, IOException {

		// 1) 파일이 없으면 아무것도 안 함
		if (file == null || file.isEmpty()) {
			return null;
		}

		// 2) 원본 파일명
		String originalName = file.getOriginalFilename();

		// 3) 확장자 추출 (마지막 점 기준)
		String ext = "";
		int dotIndex = originalName.lastIndexOf(".");
		if (dotIndex > -1) {
			ext = originalName.substring(dotIndex);
		}

		// 4) 겹치지 않는 새 파일명
		String saveName = UUID.randomUUID() + ext;

		// 5) 폴더가 없으면 생성
		File dir = new File(uploadDir).getAbsoluteFile();
		if (!dir.exists()) {
			dir.mkdirs();
		}

		// 6) 실제 저장
		File target = new File(dir, saveName);
		file.transferTo(target);

		// 7) 결과 반환
		String path = webPrefix + "/" + saveName;

		return new SavedFile(originalName, saveName, path);
	}


	public boolean delete(String webPath, String uploadDir) {

		if (webPath == null || webPath.isEmpty()) {
			return false;
		}
		if (uploadDir == null || uploadDir.isEmpty()) {
			return false;
		}

		// 웹 경로에서 파일명만 추출
		String fileName = webPath.substring(webPath.lastIndexOf("/") + 1);

		File target = new File(new File(uploadDir).getAbsoluteFile(), fileName);

		if (target.exists()) {
			target.delete();
		}

		return true;
	}
}
파일명을 UUID로 바꾸는 이유 3가지
  1. 덮어쓰기 — A와 B가 둘 다 자격증.png 를 올리면 A의 파일이 사라진다
  2. 한글·공백 — 내 자격증(최종).png 는 서버·URL에서 깨질 수 있다
  3. 보안 — 파일명으로 개인정보가 노출되거나 주소를 추측당할 수 있다

원본 이름은 SavedFile.originalName 에 따로 보관한다.

값용도
실제 저장 위치C:\dev\...\0_fixer\uploads\license\a3f2.png서버 디스크

판단 기준: 생성된 PK를 자바 코드에서 다시 쓸 일이 있나?

  • 있으면 <selectKey order="BEFORE"> — 미리 뽑아 DTO에 채움
  • 없으면 SQL 안에서 SEQ_XXX.NEXTVAL 직접 사용

기타 규칙

  • 컬럼명을 반드시 나열 — INSERT INTO T VALUES (...) 는 컬럼 순서에 의존해서 나중에 조용히 망가진다
  • 안 적은 컬럼은 NULL — 승인시각·거절사유는 심사 전이라 비워두는 게 맞다
  • DEFAULT SYSTIMESTAMP 컬럼은 생략 — UPLOADED_AT 은 DB가 직접 찍는 게 정확하다
  • ORDER BY 없으면 순서가 보장되지 않는다 — 화면 목록은 항상 정렬
  • UPDATE/DELETE 는 WHERE 부터 쓰고 앞을 채운다 — 실무 사고 1순위

FixerServiceImpl (구현체)

@Service
@RequiredArgsConstructor
public class FixerServiceImpl implements FixerService {

	private final FixerMapper mapper;
	private final FileUploadUtil fileUploadUtil;

	@Value("${file.upload-dir.license}")
	private String licenseUploadDir;


	@Override
	public List<CategoryDTO> getCategoryList() {
		return mapper.selectCategoryList();
	}


	@Override
	@Transactional(rollbackFor = Exception.class)
	public void applyVerify(String userId, FixerVerifyRequest request)
			throws IllegalStateException, IOException {

		// ---------- 1) 현재 신청 상태 확인 ----------
		FixerProfileDTO profile = mapper.selectFixerProfile(userId);

		boolean isNew;

		if (profile == null) {
			isNew = true;                                     // 신규

		} else if ("PENDING".equals(profile.getFixerApproval())) {
			throw new IllegalStateException("이미 심사 중인 신청이 있습니다.");

		} else if ("APPROVED".equals(profile.getFixerApproval())) {
			throw new IllegalStateException("이미 인증된 기사입니다.");

		} else {
			isNew = false;                                    // REJECTED → 재신청
		}


		// ---------- 2) 재신청이면 기존 데이터 정리 ----------
		List<FixerLicenseDTO> oldLicenses = null;

		if (!isNew) {
			// 파일 경로를 미리 확보 (DB에서 지우면 경로를 알 수 없게 됨)
			oldLicenses = mapper.selectLicensesByFixerId(userId);

			mapper.deleteLicensesByFixerId(userId);
			mapper.deleteRegionsByFixerId(userId);
			mapper.deleteCategoriesByFixerId(userId);
		}


		// ---------- 3) 프로필 저장 ----------
		FixerProfileDTO saveProfile = new FixerProfileDTO();
		saveProfile.setUserId(userId);
		saveProfile.setFixerIntro(request.getFixerIntro());
		saveProfile.setFixerCareer(request.getFixerCareer());

		if (isNew) {
			mapper.insertFixerProfile(saveProfile);
		} else {
			mapper.updateFixerProfile(saveProfile);
		}


		// ---------- 4) 지역 / 분야 / 자격증 저장 ----------

		// 4-1) 활동 지역
		if (request.getRegionNames() != null) {
			for (String regionName : request.getRegionNames()) {
				mapper.insertFixerRegion(userId, regionName);
			}
		}

		// 4-2) 수리 분야
		if (request.getCategoryIds() != null) {
			for (String categoryId : request.getCategoryIds()) {
				mapper.insertFixerCategory(userId, categoryId);
			}
		}

		// 4-3) 자격증 (이름 · 번호 · 파일이 같은 순서로 짝을 이룸)
		List<MultipartFile> files = request.getLicenseFiles();
		List<String> names = request.getLicenseNames();
		List<String> nos   = request.getLicenseNos();

		if (files != null) {
			for (int i = 0; i < files.size(); i++) {

				SavedFile saved = fileUploadUtil.save(
						files.get(i), licenseUploadDir, "/uploads/license");

				if (saved == null) {
					continue;                    // 파일을 안 올린 칸은 건너뜀
				}

				String name = (names != null && i < names.size()) ? names.get(i) : null;
				String no   = (nos   != null && i < nos.size())   ? nos.get(i)   : null;

				if (name == null || name.isBlank()) {
					throw new IllegalStateException("자격증명을 입력해주세요.");
				}

				FixerLicenseDTO license = new FixerLicenseDTO();
				license.setFixerId(userId);
				license.setLicenseName(name);
				license.setLicenseNo(no);
				license.setLicenseFile(saved.getPath());

				mapper.insertFixerLicense(license);
			}
		}


		// ---------- 5) 옛 파일 삭제 (모든 DB 작업이 끝난 뒤) ----------
		if (oldLicenses != null) {
			for (FixerLicenseDTO old : oldLicenses) {
				fileUploadUtil.delete(old.getLicenseFile(), licenseUploadDir);
			}
		}
	}
}

구간별 핵심

구간핵심
1) 상태 확인null 검사를 제일 먼저. "PENDING".equals(x) — 상수를 앞에 두면 NPE 방지 (요다 조건문)
2) 기존 정리조회 → 삭제 순서. 지우고 나면 파일 경로를 알 방법이 없다. 변수는 if 밖에서 선언 (스코프)
3) 프로필화면용 Request → DB용 DTO 변환이 서비스의 일. #{} 로 표시된 값만 채운다
4) 자식 저장지역·분야는 향상된 for, 자격증은 인덱스 for (목록 3개의 순서를 맞춰야 하므로)
5) 파일 삭제되돌릴 수 없는 작업은 맨 마지막

@Transactional 함정 3가지

  1. public 이어야 한다 — private 에 붙이면 아무 일도 안 일어난다 (에러도 없음)
  2. 같은 클래스 안에서 호출하면 무시된다 — 프록시 방식이라 밖에서 들어오는 호출에만 적용
  3. 기본은 RuntimeException 만 롤백 — IOException 은 롤백 안 됨 → 그래서 @Transactional(rollbackFor = Exception.class)

어노테이션 — 스프링에게 남기는 쪽지

어노테이션은 그 자체로는 아무 일도 하지 않는다. 누군가 읽고 행동해야 의미가 생긴다. 택배 상자의 취급주의 스티커가 상자를 지켜주는 게 아니라, 기사님이 그걸 보고 조심히 다루는 것과 같다.

1. 실행 시작 2. 모든 클래스를 훑는다 ← 컴포넌트 스캔 3. @ 표시가 붙은 클래스를 발견 4. 표시 종류에 따라 다르게 처리 5. 만든 객체들을 컨테이너에 보관
스캔 범위 — 모든 클래스는 com.fixer 아래에

@SpringBootApplication 이 붙은 클래스의 패키지와 그 하위만 훑는다. 밖에 만들면 어노테이션이 무시되어 "코드를 썼는데 아무 반응이 없는" 상황이 생긴다.

@Bean메서드반환값을 빈으로 등록

@Controller vs @Bean

  • 내가 만든 클래스 → 클래스에 @Controller/@Service/@Component
  • 외부 라이브러리 객체 → @Configuration 클래스 안에서 @Bean 메서드로 등록 (BCryptPasswordEncoder 는 남의 코드라 표시를 붙일 수 없다)

제어의 역전 (IoC)

어노테이션 = 스프링에게 남기는 쪽지.
내가 new 로 객체를 만들고 메서드를 호출하는 대신, 표시만 해두면 스프링이 알아서 만들고 연결한다.

원래 개발자가 하던 일(객체 생성·호출)을 프레임워크가 가져갔다는 뜻으로 제어의 역전(IoC) 이라고 부른다.

  • DB부터 확인 — 화면에 메시지가 안 떠도 저장은 됐을 수 있다. 그러면 문제 범위가 절반으로 준다

F-14 마무리

  • 상태별 화면 분기 — GET에서 이미 신청했으면 폼 대신 "심사 중입니다 / 인증 완료 / 거절 사유" 표시 (난이도 쉬움 · 우선 추천)
  • 자격증 여러 개 추가 — JavaScript로 입력칸 추가 버튼 (코드는 이미 N개를 처리할 수 있게 되어 있음)
  • 입력값 검증 — 소개 필수, 지역 1개 이상, 분야 1개 이상, 파일 확장자 제한
  • 로그인 세션 연결 — String userId = "fixer01"; 하드코딩 제거

팀에 공유해야 할 사항

① 스키마 스크립트 수정본 공유

원본 ERD 출력물은 어느 DB에서도 실행되지 않는다. Oracle용으로 변환한 버전을 sql/schema.sql 로 저장소에 올리고 팀에 공지할 것.

② FIXER_PROFILE PK 누락

원본에 PK_FIXER_PROFILE 이 없다. 없으면 "1인 1신청"이 코드로만 지켜지고 DB는 막아주지 않는다.

③ CATEGORY_ID 과다 중복 (정규화 위반)

CHAT_MESSAGE, REPAIR_PHOTO, RECEIPT_ITEM, ESTIMATES_OPTION 에까지 CATEGORY_ID NOT NULL 이 붙어 있다. 이들은 부모를 타고 올라가면 카테고리를 알 수 있으므로 같은 정보를 여러 곳에 중복 저장하는 구조. 값이 어긋날 위험이 있으니 ERD 확정 전에 정리 권장.

단, FIXER_CATEGORY.CATEGORY_ID 는 그 자체가 매핑 테이블이므로 정당하다.

④ 거절 사유 표시 정책

FIXER_REJECT_REASON 을 기사에게 보여줄지, 관리자만 볼지 관리자 기능 담당자와 합의 필요.

⑤ REGION 공통 코드 테이블 부재

선택 가능한 지역 목록을 가진 테이블이 없어 현재 JSP에 하드코딩되어 있다. 공통 코드 테이블을 만들거나 주소 API 사용을 검토할 것.

⑥ 문법 오류 2건

USERS·CATEGORY·ADMIN 의 닫는 괄호 중복, USER_ADDRESS.IS_DEFAULT 의 DEFAULT NUMBER(1) → DEFAULT 0
